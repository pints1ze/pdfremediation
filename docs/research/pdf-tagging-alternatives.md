# Open-source alternatives to Mistral OCR and PDFix for tagging

Research date: 2026-11-26. Every version, licence and date below was checked against the primary source linked next to it on that date. Anything marked **unverified** could not be confirmed from a primary source. None of this is legal advice. Before launch, have counsel confirm the licence findings, especially the AGPL, CC-BY-NC and custom-licence flags.

## 1. Recommendation

| Area | Recommended | Runner-up |
|---|---|---|
| **Writing the tag tree** onto the original PDF | **OpenDataLoader PDF** (Apache-2.0, Java sidecar). It is the only open-source project found that already rewrites page content streams with BDC/EMC + MCIDs, marks the rest as Artifact, and builds StructTreeRoot and ParentTree on the original file. Feed it our structure, then add a small PDF/UA-1 finishing pass (XMP `pdfuaid`, `/Lang`, title, `DisplayDocTitle`). | **A custom writer on Apache PDFBox 3.0** (Apache-2.0, Java sidecar). It has every low-level primitive needed, including incremental save, but the writer itself is a large build (see §2.3). |
| **Understanding** (layout, reading order, tables) | **Docling** standard pipeline via `docling-serve` (MIT code; Heron layout weights Apache-2.0; TableFormer weights CDLA-Permissive-2.0/Apache-2.0). Python sidecar, runs on CPU, GPU optional. OpenDataLoader already consumes Docling output natively. | **PaddleOCR 3.x** (PP-StructureV3 / PaddleOCR-VL-1.5; Apache-2.0 code and weights). Strong on tables and reading order, but the VL model in practice needs a GPU. |
| **Alt text drafts** | **Qwen3-VL-8B-Instruct** (Apache-2.0 weights), self-hosted, GPU. | **Granite-Vision-3.3-2B** (Apache-2.0), which plugs into Docling's picture-description stage and is smaller. |
| **OCR text layer** for scanned pages | **OCRmyPDF 17.x** (MPL-2.0) with Tesseract 5 (Apache-2.0), run in Preprocessing with `--output-type pdf --optimize 0`, the pypdfium2 rasterizer and no rotate/deskew/clean options. It adds an invisible (render mode 3) text layer on top of the original page. | Emit the invisible text ourselves from OCR word boxes, using Tesseract's GID-1 "glyphless" font technique (Apache-2.0), inside the same writer that assigns MCIDs. |
| **Rendering for the pixel diff** | **PDFium** (BSD-3-Clause/Apache-2.0) through **PDFtoImage** (MIT, native .NET NuGet), with `bblanchon.PDFium.*` pinned to an exact version and run in one pinned Linux container image. | **pypdfium2** (Apache-2.0/BSD-3-Clause) in the Python sidecar. It is the same engine, so either choice gives identical results if the same PDFium build is pinned. |

**Overall shape:** .NET web app and worker. One Java sidecar (OpenDataLoader + veraPDF; both are JVM projects, and veraPDF is already required). One Python sidecar (Docling/docling-serve, OCRmyPDF, optionally a VLM server). Rendering stays in-process in .NET. Nothing in this stack charges per page or needs a subscription. The costs are compute (CPU, optionally a GPU for the VLM) and two extra container images to operate.

**Plain statement on the crux:** no permissively licensed library offers "take this external structure description and write a PDF/UA-1 tag tree onto the existing content" as a finished API. OpenDataLoader comes closest. It does the content-stream rewriting and structure-tree building, but it expects its own extraction model as input, and its free tier stops at "Tagged PDF" (PDF/UA export is a paid enterprise add-on). Using it for this product means writing a Java adapter from our Accessibility IR into its model (or into DoclingDocument JSON, which it already ingests), plus a finishing pass for PDF/UA-1 metadata. Both pieces are bounded. Building the equivalent from scratch on PDFBox, PdfPig or qpdf is a large job: OpenDataLoader's tag-writing layer alone is about 160 KB of Java (§2.3).

## 2. Writing the tag tree without visual change

### 2.1 What has to happen

On the original file, the writer must:

- parse every page and Form XObject content stream;
- map each painting operator (text show, path paint, `Do`, inline image, `sh`) to an IR Element or to Artifact;
- wrap the operators in `BDC /Tag <</MCID n>> … EMC` or `/Artifact BMC … EMC` without changing any graphics state;
- build `StructTreeRoot`, `ParentTree` and `ParentTreeNextKey`, `/StructParents` on pages and forms, `RoleMap` where custom types are used, `MarkInfo /Marked true`, `/Lang`, `dc:title` + `ViewerPreferences/DisplayDocTitle`, and `pdfuaid:part=1` in XMP.

veraPDF checks each of these. For example, rule 7.1-3 requires "Content shall be marked as Artifact or tagged as real content", 7.1-8 requires catalog Metadata, and 7.1-10 requires `DisplayDocTitle == true` ([7.1 profile directory](https://github.com/veraPDF/veraPDF-validation-profiles/tree/integration/PDF_UA/1/7.1%20General)).

### 2.3 How big the custom-writer job is (for the PDFBox runner-up)

OpenDataLoader shows what "done" looks like:

- `AutoTaggingProcessor.java` is 111 KB / 2,142 lines;
- `ChunksWriter`, `FormUses`, `PaintBounds`, `PagePaints` and `ContentStreamTokens` add about 50 KB ([tree](https://github.com/opendataloader-project/opendataloader-pdf/tree/main/java/opendataloader-pdf-core/src/main/java/org/opendataloader/pdf));
- all of that sits on veraPDF's graphics-state and glyph-geometry model.

Its comments record edge cases found the hard way. Forms drawn more than once can have only one `/StructParents`, so their content must become Artifact (PDF/UA-1 7.20). Path-construction operators must sit inside the same BDC as their paint operator. Notes need unique `/ID`s ([source comments](https://github.com/opendataloader-project/opendataloader-pdf/blob/main/java/opendataloader-pdf-core/src/main/java/org/opendataloader/pdf/processors/AutoTaggingProcessor.java)).

My estimate (**not a measured figure**) for a from-scratch PDFBox writer of similar quality: 5–10k lines of code, and several months of corpus-driven edge-case work. That is beyond the PRD's two-junior-developer, eight-week plan. Adopting OpenDataLoader and writing an adapter is far smaller: probably 1–3k lines of Java plus tests (again an estimate).

### 2.4 Known OpenDataLoader risks for zero-pixel-diff and ADR 0001

- **Existing marked content is dropped wholesale.** `ChunksWriter.processOperator` discards every `BMC`, `BDC` and `EMC` it finds (`case BMC/EMC/BDC: break;`) ([source](https://github.com/opendataloader-project/opendataloader-pdf/blob/main/java/opendataloader-pdf-core/src/main/java/org/opendataloader/pdf/autotagging/ChunksWriter.java)). That fits ADR 0001 for old structure tags. But it would also drop **optional-content** `BDC /OC /MCx … EMC` sequences, which can make hidden layers visible. No `/OC` handling was found in that file or in `AutoTaggingProcessor` (**unverified** whether it is handled elsewhere). Expect to patch this upstream.
- **Content streams are re-serialised from tokens**, and streams over 100,000 tokens are split into arrays ([source](https://github.com/opendataloader-project/opendataloader-pdf/blob/main/java/opendataloader-pdf-core/src/main/java/org/opendataloader/pdf/processors/AutoTaggingProcessor.java)). Number formatting, string encoding and inline-image round-tripping must be bit-faithful. **Unverified**: test it on the corpus.
- **The old StructTreeRoot is replaced by a new one** (`createStructTreeRoot` sets a new catalog entry), so the old tree becomes orphaned objects. That matches ADR 0001, but it does not explicitly clean old `/StructParent(s)` keys on annotations (**unverified**).
- **One document per JVM at a time:** `tagDocument` is `static synchronized` and uses static mutable maps. Scale by process count.
- **Free-tier output is "Tagged PDF", not PDF/UA-1.** The finishing pass must add `pdfuaid:part=1` XMP, `dc:title`, `DisplayDocTitle`, `/Lang`, and whatever else veraPDF reports. Which PDF/UA-1 rules OpenDataLoader's free output already passes is **unverified**.
- **For scans, OCR text without an underlying text layer is tagged differently.** It becomes `/ActualText` over the paint operators, or is discarded if nothing was painted ([source comments around `processDrawnText` / `discardIfEmpty`](https://github.com/opendataloader-project/opendataloader-pdf/blob/main/java/opendataloader-pdf-core/src/main/java/org/opendataloader/pdf/processors/AutoTaggingProcessor.java)). That is why §4 adds a real invisible text layer before tagging.

### 2.5 How our IR gets into OpenDataLoader

There are two options, both **unverified** until T-005:

1. **Via its hybrid interface.** OpenDataLoader's `HybridClient` receives "JSON structured document format (DoclingDocument)" from a backend ([HybridClient.java](https://github.com/opendataloader-project/opendataloader-pdf/blob/main/java/opendataloader-pdf-core/src/main/java/org/opendataloader/pdf/hybrid/HybridClient.java)). Our IR maps cleanly onto DoclingDocument ([docling-core](https://github.com/docling-project/docling-core), MIT), so a custom `HybridClient` that returns our IR as DoclingDocument JSON would reuse OpenDataLoader's whole bbox-to-operator matching. The open question is whether `--hybrid-mode full` keeps backend structure without OpenDataLoader re-deriving it.
2. **Via its Java API.** Run OpenDataLoader's extraction to get content chunks with operator provenance, rebuild the semantic tree from our IR, then call `AutoTaggingProcessor.tagDocument(document, contents, pdfVersion)` directly ([AutoTagger.java](https://github.com/opendataloader-project/opendataloader-pdf/blob/main/java/opendataloader-pdf-core/src/main/java/org/opendataloader/pdf/api/AutoTagger.java)).

## 6. Risks and unknowns, and what T-005 should test first

The tests are in priority order.

1. **Zero-pixel-diff through OpenDataLoader.** On a corpus covering optional content (OCGs), inline images, Type 3 fonts, shared Form XObjects, annotations, rotated and UserUnit pages, and huge streams: tag, then render both files with pinned PDFium and diff. Fix the `/OC` drop (§2.4) first if it shows up.
2. **IR → OpenDataLoader adapter feasibility.** Prove one born-digital and one OCR'd scanned page can be tagged from *our* IR, via a custom `HybridClient` or the Java API (§2.5), and that OpenDataLoader does not override the IR's reading order or roles.
3. **veraPDF PDF/UA-1 failures after the finishing pass.** List which rules the free OpenDataLoader output still fails once `pdfuaid`, title, `DisplayDocTitle` and `/Lang` are added. This decides how much Repair-pass code is needed, and feeds the failure-rate pricing input already in §14.
4. **Already-tagged inputs (ADR 0001).** Confirm the old tree and old marked content are fully replaced, no stale `/StructParent` keys remain, and the result passes veraPDF.
5. **OCR layer.** Run OCRmyPDF with the settings in §4 → pixel diff = 0 → veraPDF 7.21.x passes with the glyphless font → Docling reads the invisible text.
6. **Mixed pages** (a scanned image plus a native header on the same page). OCRmyPDF's skip-text mode skips any page that already has text, so these may get no OCR. This may need per-region OCR written by our own code (the §4 runner-up).
7. **Docling quality and per-Element confidence.** Benchmark on the annotated corpus. Confirm per-cluster confidence can be surfaced as `Element.confidence` (GLOSSARY requires per-Element confidence; Docling's public grades are per page).
8. **Throughput and sizing.** OpenDataLoader is single-document per JVM; Docling on CPU; Qwen3-VL on GPU. The PRD target is 30,000 pages/month (A-23).
9. **Upstream churn.** OpenDataLoader releases weekly and its core tagging class carries static state. Pin versions, keep patches as upstream PRs, and fork if needed (Apache-2.0 allows it).
10. **Licence hygiene.** Keep NOTICE files (Apache-2.0). Publish source for any modified MPL-2.0 files (veraPDF, OCRmyPDF, pikepdf). Never pull AGPL/NC weights (MinerU2.5-2509, Surya, DocLayout-YOLO code). Re-check model-card licences whenever a model is upgraded.

## 7. What this changes in the PRD

Adopting this stack **replaces both named vendors**. Concretely:

- **Mistral OCR 4.1 → Docling (self-hosted) + OCRmyPDF/Tesseract + Qwen3-VL for alt text.**
  - Affects §1, Goals bullet 7, §6 "Understanding", §10.2, INT-01, A-18, A-51, SC-03 and SC-07: cost per page becomes compute cost, not `$0.004/page`.
  - The §10.2 IR contract stays; only the adapter changes.
  - OQ-05 (Mistral contract, data residency) mostly goes away: documents never leave our infrastructure. That is a plus for government data (OQ-07).
- **PDFix Enterprise → OpenDataLoader PDF (Java sidecar), plus a PDF/UA-1 finishing pass (PDFBox or PdfPig incremental update).**
  - Affects §1, Goals bullet 9, §6 "Remediation", §10.3 (the worker request/response contract can stay), INT-02, A-19, A-21, A-48 (no licensed-worker cap), §13.1 constraint bullets 5 and 8, the first two rows of §14, and OQ-04, which is no longer needed.
  - The "Unlicensed elastic PDFix worker creation" exclusion in §6 disappears.
- **Non-goals to revisit:**
  - "will not self-host … Docling, or MinerU" (line 45) would have to be reversed for Docling; MinerU stays excluded on licence grounds.
  - "will not build a PDF tagging engine directly on Apache PDFBox" (line 47) still holds for the primary path, because OpenDataLoader is adopted rather than built. The PDFBox runner-up would contradict it.
- **OQ-10** is answered in part: PDFium, pinned through `bblanchon.PDFium`.
- **T-005** becomes "render → OCRmyPDF → Docling → IR → OpenDataLoader adapter → finishing pass → veraPDF → PDFium diff", with the priority tests in §6. The release-gate wording about "acceptable PDFix SaaS rights" becomes "OpenDataLoader preserves rendering and accepts our IR".
- **New operational costs:** two sidecar images (JVM and Python) to build, pin and patch. An optional GPU node, needed only for VLM alt text or VLM OCR fallback. Upstream-patch maintenance for OpenDataLoader.
